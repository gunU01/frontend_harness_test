# PRD 작성 도구

한 줄 문제 정의만 넣으면 내 문서 템플릿(섹션 + hint)에 맞춰 AI가 초안을 채워주는 개인용 도구입니다. 처음엔 PRD 한 종류만 지원했지만, "PM을 위한 문서 작성 도구"로 포지셔닝을 넓히면서 회의록 등 여러 문서 타입을 등록·전환하고, 완성한 문서를 팀에 공개 공유할 수 있게 확장했습니다. 이 레포는 "PM은 무엇을 만들지보다, 무엇을 결정하는가" 강의의 실제 사례(case study)로 쓰기 위해 기획→개발→배포를 하네스(오케스트레이터 + 서브에이전트: planner/builder/styler/reviewer)로 진행했습니다.

이 제품 자체의 기획(문제/근거/목표/하지 않을 것/해결 방향/리스크/출시 계획)은 `PLANNING.md`에 있습니다 — 이 도구가 사용자에게 만들어주는 것과 같은 템플릿 구조로, 새 기능을 넣기 전에 먼저 갱신하는 "기획 하네스"로 씁니다.

## 스택

- Vite + React + TypeScript + Tailwind CSS (프론트엔드)
- Firebase Auth(Google 로그인) + Firestore (별도 서버 없이 프론트에서 직접 연동)
- Firebase Functions (`onCall` 단일 함수, Anthropic API 프록시)

## 화면

로그인 후 화면(`/specs`, `/specs/new`, `/specs/:id`, `/settings`, `/analytics`)은 공통 헤더(`AppHeader`)로 이동합니다. `/`, `/signin`, `/community`, `/community/:id`는 헤더 없는 공개 화면입니다.

- **홈** (`/`): 로그인 여부에 따라 시작하기/스펙 목록 버튼만 있는 랜딩
- **설정** (`/settings`): 좌측에 내 문서 타입 목록(PRD, 회의록, ... — 추가·삭제), 우측에 선택된 타입의 섹션 편집(제목/hint, 추가·삭제·순서변경). 아래에 전체 문서 타입이 공유하는 제품 설명(`productContext`)·용어집(`glossary`)
- **목록** (`/specs`): 작성 중인 스펙 카드 (문서 타입 라벨 + draft/review/done 상태뱃지)
- **새 스펙 만들기** (`/specs/new`): 문서 타입을 카드 갤러리에서 고른 뒤 제목/한줄정의를 입력하는 2단계 플로우 (예전엔 `/specs`의 인라인 `<select>`였음)
- **작성** (`/specs/:id`): 왼쪽 섹션 목록, 오른쪽 편집. 버튼 3개 — 초안 생성 / 이 섹션 다시 쓰기 / 빈틈 지적. "커뮤니티에 공개하기" 체크박스로 발행 여부 전환
- **커뮤니티** (`/community`, 공개, 로그인 불필요): 발행된 스펙을 카드로 둘러보는 목록
- **커뮤니티 상세** (`/community/:id`, 공개): 발행된 스펙 하나를 읽기 전용으로 표시. 작성자 정보는 노출하지 않음 (익명)
- **분석** (`/analytics`): "내 활동 분석" — 본인 이벤트만 본인이 보는 개인용 대시보드/퍼널/리텐션 3탭. 다른 사용자 데이터는 보이지 않음

## 데이터 구조

```
config/{uid}
  templates: [{ id, name, sections: [{ key, title, hint }] }]
  productContext: string
  glossary: string

specs/{specId}
  uid, authorName, title, oneLiner, status, templateId, docType, published
  sections: [{ key, title, hint, content }]
  risks: [{ id, text, resolved }]
  stakeholders: [{ id, name, confirmed }]
  createdAt, updatedAt

events/{eventId}   # append-only, 본인만 생성/읽기 가능, 수정·삭제 전부 금지
  uid, name, properties, timestamp
```

`published`가 `true`면 `/community/:id`에서 로그인 없이 읽을 수 있습니다. `firestore.rules`가 `specs`의 읽기 조건을 "작성자 본인 또는 `published == true`"로 분기하고, 쓰기(생성/수정/삭제)는 여전히 작성자 본인만 가능합니다 — `config/{uid}`(제품 설명·용어집)는 이 변경과 무관하게 항상 비공개입니다. `published==true` 목록 조회에 필요한 복합 색인은 `firestore.indexes.json`에 정의되어 있습니다.

스펙은 생성 시점의 템플릿(섹션 제목·hint까지)을 통째로 스냅샷으로 복사합니다 — 나중에 설정에서 템플릿을 고쳐도 이미 만든 스펙은 영향받지 않고, Functions도 `config.templates`를 다시 찾을 필요 없이 `spec.sections`만 읽으면 됩니다.

## 디자인 시스템

Figma에 별도 파일로 구축했습니다: [PRD 작성 도구 디자인 시스템](https://www.figma.com/design/Eqfw554mL4YxqKbcXRq3su)

- **레퍼런스**: KRDS(대한민국 정부 디지털서비스 디자인시스템 — 중립적이고 접근성 중심인 톤)와 토스 디자인시스템(부드러운 radius, 신뢰감 있는 브랜드 블루, 절제된 컴포넌트 수)을 일반적으로 알려진 원칙 수준에서 참고했습니다. 개인이 링크로 준 블로그 글 3개는 이 환경의 네트워크 정책상 접근이 막혀 있고 제가 내용을 알지 못해 반영하지 않았습니다 — 모르는 걸 아는 척 반영하지 않기 위한 선택입니다.
- **범위**: `figma-generate-library` 스킬이 요구하는 "프로덕션급"(20~100회 작업, 전체 문서화, Code Connect)은 1인 프로젝트 규모에 비해 과해서 의도적으로 줄였습니다.
- **v2**: 첫 버전(컬러 3~4단만 지정, 컴포넌트가 단일 variant)이 허술하다는 피드백을 받아, 색상 램프를 50~900 10단계로 넓히고 컴포넌트에 실제 다축 variant(State 등)를 추가.
- **v3 (사용자가 첨부한 실제 레퍼런스로 재정렬)**: 사용자가 Figma "Foundations" 페이지에 실제 참고 자료(Toss 스타일 Primitive 팔레트, Light/Dark 시맨틱 토큰 테이블, 타이포 스케일)를 직접 붙여줘서, v2의 제 임의 HSL 공식 대신 그 자료의 **정확한 hex 값·토큰 이름·구조**를 그대로 따랐습니다:
  - Primitives: Blue/Grey 50~900 10단계, Red/Green/Yellow는 자료에 있는 50·100·300·500·700 5단계만 (없는 값을 지어내지 않음)
  - Semantic: `text/primary`·`background/brand`·`border/default`·`status/success` 같은 자료의 토큰 이름 그대로, **Light/Dark 2모드**로 구성 (앱 코드에는 아직 다크모드 UI가 없어 Figma 쪽에만 존재 — 필요해지면 그대로 꺼내 쓸 수 있음)
  - Typography: 자료의 `Toss/Display1~Caption2` 9단계를 크기·줄간격·자간까지 그대로 반영
  - 배지 텍스트 색은 예외적으로 자료의 500 기반 `status/*` 대신 700 계열 primitive를 직접 썼습니다 — 500 값은 저채도 배경 위 아이콘/점 용도로는 맞지만 작은 텍스트로 쓰기엔 명도 대비가 부족해서(WCAG AA 미달 우려), 대비가 확실한 값으로 바꿨습니다.
- **코드 반영**: `tailwind.config.js`의 `primary` 50~900을 Figma Blue 램프와 정확히 동일한 hex로 재동기화했고, 버튼 기본색을 `primary-600`(추정치) → `primary-500`(자료의 `background/brand` 값)으로, hover를 `primary-700` → `primary-600`으로 맞췄습니다.
- **화면 목업**: "Screens" 페이지에 `SpecList`·`SpecEditor`·`NewSpec`(템플릿 갤러리)·`Community` 화면을 컴포넌트 인스턴스로 조립해뒀습니다 (컴포넌트가 실제로 재사용 가능한지, 토큰 교체 후에도 다시 연결되는지 검증하는 용도).
- **v4 (공통 네비 + 신규 화면)**: `AppHeader` 컴포넌트를 새로 추가하고, 참고하려던 5개 사이트(토스 커리어 커뮤니티, 신한프렌즈 디지털상품, 아토미, 포스텍, 국립환경과학원)는 이번에도 전부 네트워크 정책상 접근이 막혀서 실제 화면은 못 봤습니다 — 그 사이트들의 정확한 비주얼을 베끼는 대신, 사용자가 콕 집어 확인해준 의도(공개 사례/커뮤니티 페이지, 템플릿 갤러리, 공통 네비게이션)만 기존 토큰/컴포넌트로 구현했습니다.
- **v5 (중립색 우선 방향 전환)**: 사용자가 실제 화면 스크린샷(디스콰이엇·벨로그·Notion·Confluence)을 직접 캡처해서 줬습니다. 이번엔 hex 값 같은 정확한 토큰 정보가 없어서 색상표를 새로 뽑진 않고, **공통으로 관찰되는 패턴**만 반영했습니다: 선택된 항목을 원색으로 채우지 않고 중립 회색 배경+굵은 글씨로 표시(모든 레퍼런스의 공통점), 파란색은 실제 핵심 액션 버튼에만 남기고 장식적 사용을 줄임, 카드에 상대시간 메타정보 한 줄 추가(벨로그), 빈 상태에 CTA 링크 추가(벨로그) — 이 CTA는 겸사겸사 `/community`가 로그인 화면으로 못 돌아가는 문제도 해결합니다. 다크 테마로 캡처된 화면들이었지만 라이트 테마는 유지하기로 확인받았습니다.


## 사용자가 직접 해야 하는 것 (이 하네스가 대신 할 수 없는 부분)

이 세션에는 Firebase 콘솔/결제 계정, `firebase login` 자격 증명이 없어 아래는 로컬/콘솔에서 직접 진행해야 합니다.

1. Firebase 콘솔에서 프로젝트 생성 → Authentication(Google 로그인 활성화), Firestore(프로덕션 모드, 리전 `asia-northeast3`), Hosting 켜기. 요금제는 Functions를 쓰려면 Blaze로 전환 (개인 사용량이면 사실상 무료, 불안하면 예산 알림 5달러 설정).
2. `npm i -g firebase-tools && firebase login`
3. `firebase functions:secrets:set ANTHROPIC_API_KEY`
4. `firebase deploy` (Firestore rules + Functions + Hosting 실배포)
5. `public/icon-192.png`, `public/icon-512.png` 추가 (manifest가 참조하지만 아직 실제 파일은 없음 — 아무 이미지나 넣어도 됩니다)

## GitHub Pages 프리뷰 배포

`.github/workflows/deploy-pages.yml`이 `claude/pm-lecture-planning-8rzvpl` 브랜치 푸시마다 정적 빌드를 GitHub Pages로 배포합니다 (레포 Settings → Pages → Source를 "GitHub Actions"로 설정 필요). Firebase 프로젝트를 만들었다면 레포 Secrets에 `VITE_FIREBASE_*` 값을 등록해야 로그인/Firestore가 실제로 동작합니다. Functions(AI 생성)는 Pages에서 동작하지 않으므로 실제 사용은 `firebase deploy`로 배포한 Firebase Hosting 쪽에서 확인하세요.

## 기능을 버린다 — 이번 스코프에서 뺀 것과 이유

이 강의 커리큘럼의 6챕터("기능을 버린다")를 그대로 이 프로젝트에 적용한 결과입니다.

| 뺀 기능 | 왜 뺐는가 |
|---|---|
| 버전 히스토리 / 되돌리기 | 1인 사용 도구라 충돌·분실 리스크가 낮음. 나중에 `updatedAt` 스냅샷만 남기는 방식으로 저비용 추가 가능 — 지금은 편집 자체를 끝내는 게 우선 |
| 코멘트 / 리뷰어 초대 | 이 도구는 "쓰는 사람" 1인 기준. 협업 리뷰는 완전히 다른 권한 모델(Firestore rules 재설계)이 필요해 범위가 커짐 |
| 검색 | 스펙 개수가 적을 개인 사용 단계에선 목록 스크롤로 충분 |
| 공유 / 퍼블릭 링크 | 인증 없는 접근 경로를 새로 열어야 해서 보안 범위가 커짐. 필요해지면 별도 스코프로 → **나중에 "공개 커뮤니티" 기능으로 다시 도입함, 아래 "두 번째 확장" 참고** |
| 마크다운 프리뷰 | textarea 하나로 충분한 "못생겨도 되는" 단계. 에디터를 잘 만들려다 시간을 다 쓰는 게 주말 MVP의 가장 흔한 실패 패턴 |
| 드래그 앤 드롭 섹션 순서변경 | 라이브러리 없이 위/아래 버튼으로 5분이면 끝나는 기능. 드래그 구현에 드는 시간 대비 이득이 없음 |
| 오프라인 캐싱 / 서비스워커 | 개발 중 옛날 버전이 계속 뜨는 문제만 만들고, 이 앱엔 오프라인 이득이 없음 |
| Functions를 draft/section/critique 3개로 분리 | 프롬프트 조립 로직이 세 군데로 흩어지는 걸 막기 위해 `mode` 파라미터 하나로 통일 |
| 과거 스펙 전체를 컨텍스트로 주입 | 최근 3개 제목+요약 정도만 주는 게 맞음 (전체를 주면 출력이 그대로 베끼는 경향) — 지금 `generate.ts`는 아직 이 부분 미구현, 다음 이터레이션 후보 |

각 항목은 "언젠가 하면 좋은 기능"이 아니라 "지금 스코프에서 명시적으로 뺀 이유가 있는 결정"입니다 — 강의에서 그대로 보여줄 의사결정 로그이기도 합니다.

## 범위를 넓힌다 — 왜 이번엔 반대로 넓혔는가

MVP 이후 첫 확장으로 "문서 타입 다양화"(PRD 외 회의록 등)를 골랐습니다. 위 표에서 뺀 항목들과 달리, 이건 제품의 포지셔닝 자체("PRD 도구" → "PM을 위한 문서 작성 도구")를 바꾸는 결정이라 별도로 남깁니다.

- **왜 이걸 먼저 넓혔는가**: 검토했던 다른 확장(에디터에 마크다운 서식·목차 추가)은 "기능을 버린다" 표에서 이미 한 번 명시적으로 뺐던 항목입니다. 뺀 이유를 뒤집을 새 근거 없이 되살리는 것보다, 아직 손대지 않은 방향(문서 타입)을 넓히는 쪽이 이전 결정과 앞뒤가 맞습니다.
- **얼마나 넓혔는가**: 템플릿을 하나에서 여러 개로 늘렸지만, 여전히 사람이 화면에서 직접 등록하는 구조입니다 — 문서 타입 마켓플레이스나 AI가 알아서 새 템플릿을 제안하는 기능은 넣지 않았습니다. "PM 문서 전반"이라는 포지셔닝은 넓혔지만, 그걸 위해 필요한 최소한(템플릿 여러 개 저장·전환)만 만들었습니다.
- **스냅샷 설계를 유지한 이유**: 템플릿이 여러 개가 되면서 "스펙은 생성 시점 템플릿을 통째로 복사해 저장한다"는 기존 설계(위 데이터 구조 참고)가 오히려 더 중요해졌습니다 — 템플릿이 하나일 땐 이 설계가 있으나 없으나 큰 차이가 없었지만, 여러 문서 타입을 넘나들며 템플릿을 계속 고치게 되는 지금은 이게 없으면 이미 쓴 문서들이 템플릿 수정에 따라 조용히 깨질 수 있습니다.

### 두 번째 확장: 공통 네비게이션 · 템플릿 갤러리 · 공개 커뮤니티

- **왜 세 개를 한 번에**: 셋이 서로 전제 조건이라 따로 쪼개면 중간 상태가 어색합니다 — 갤러리(`/specs/new`)와 커뮤니티(`/community`)는 화면이 늘어난 만큼 이동 수단(공통 네비)이 없으면 애초에 도달할 방법이 없습니다.
- **"공유 / 퍼블릭 링크"를 다시 꺼낸 이유**: 위 "기능을 버린다" 표에서 이미 한 번 명시적으로 뺐던 항목입니다 (당시 이유: "인증 없는 접근 경로를 새로 열어야 해서 보안 범위가 커짐. 필요해지면 별도 스코프로"). 지금 다시 넣는 이유는 그 "별도 스코프"가 이번에 명확해졌기 때문입니다 — 스펙 전체를 공유하는 게 아니라 작성자가 명시적으로 "공개" 토글을 켠 문서 한 건만, 익명으로, 읽기 전용으로 공개합니다. `firestore.rules`에서 이 조건 하나만 정확히 좁혀서 넣었고 (`PLANNING.md`의 리스크 항목 참고), 쓰기 권한은 전혀 건드리지 않았습니다.
- **레퍼런스 사이트를 그대로 못 따른 이유**: 사용자가 참고해달라고 준 5개 사이트는 이번에도 네트워크 정책상 못 열어봤습니다. 성격이 서로 다른 사이트들(조직문화 블로그/상품몰/이커머스/대학/정부기관)이라 안 보고 넘겨짚으면 엉뚱하게 만들 위험이 커서, 사용자에게 "정확히 어떤 기능을 원하는지" 직접 확인받은 뒤(공개 사례 페이지 / 템플릿 갤러리 / 공통 네비) 그 의도만 기존 디자인 시스템으로 구현했습니다 — 시각적 스타일은 참고하지 못했다는 한계를 그대로 남겨둡니다.

### 세 번째 확장: 의사결정 지원 (PLANNING.md 4단계)

지금까지는 "문서를 쓰고 공유한다"까지였고, 이 강의의 주제("PM은 무엇을 만들지보다, 무엇을 결정하는가")를 도구 기능으로 직접 지원하는 건 없었습니다. 이번엔 네 개의 서브에이전트를 데이터 레이어 → UI 두 단계로 나눠 병렬로 진행했습니다(각자 건드리는 파일을 분리해 충돌 없이).

- **문서 타입 5종 추가** (기능 명세서/릴리즈 노트/실험 설계서/의사결정 로그/우선순위 스코어링): 기존 `DocTemplate` 구조 그대로 재사용. RICE/ICE 스코어링은 계산기 UI를 새로 만드는 대신 "항목별 점수와 근거를 텍스트로 적으라"는 가이드형 템플릿으로 제한했습니다 — 텍스트 에디터 안에 스프레드시트를 짓는 건 이 도구 크기에 안 맞는다고 판단.
- **가정/리스크 트래커 · 이해관계자 확인 체크리스트** (신규 데이터 구조): 이번 확장에서 유일하게 새 아키텍처가 필요했던 부분 — `spec.risks`/`spec.stakeholders` 배열을 각각 독립적으로 디바운스 저장합니다. 기존 "빈틈 지적" AI 기능이 새로고침하면 사라지던 결과물을, "가져오기" 버튼으로 트래커에 영구 저장할 수 있게 연결했습니다.
- **템플릿 마켓플레이스 연결**: 커뮤니티에 발행된 스펙에서 "이 템플릿으로 새 스펙 만들기" — 이미 있던 템플릿 갤러리·커뮤니티 두 기능을 연결한 것뿐이라 새 필드가 필요 없었습니다 (스펙에 이미 스냅샷된 `sections[].{key,title,hint}`를 그대로 재사용).
- **작성자 이름 표시**: `PLANNING.md`에 남아있던 미해결 질문(익명 유지 vs 이름 노출)을 이름 노출로 결정. uid/이메일은 여전히 노출하지 않고 표시 이름만 스냅샷.
- **커뮤니티 검색/필터**: 문서 타입 필터 + 텍스트 검색. 커뮤니티는 여러 사람 글이 쌓이는 공개 목록이라, "개인 스펙 목록엔 검색이 필요 없다"던 원래 결정(위 표 참고)과 전제가 다릅니다.
- **Firestore rules 자동화 테스트**: `VERIFICATION.md`가 유일하게 이 하네스에서 바로 자동화 가능하다고 지목했던 영역 — `firebase emulators:exec` + `@firebase/rules-unit-testing`으로 공개/비공개 읽기·쓰기 회귀 15개 시나리오를 코드로 고정했고, 이 세션에서 실제로 실행해 15/15 통과를 확인했습니다 (`npm run test:rules`).

### 네 번째 확장: 개인 활동 분석 (PLANNING.md 5단계)

"Amplitude 같은 걸 만들어줘"라는 요청에서 시작했습니다. 그대로 옮기면 여러 사용자를 한눈에 보는 관리자 대시보드가 되는데, 이 앱의 `firestore.rules`는 전부 "본인 uid만" 기준이라 정면으로 충돌합니다 — 그래서 "내 활동 분석"으로 좁혔습니다. 데이터 레이어(이벤트 트래킹+계측) → 차트 프리미티브 → 화면 조립, 3단계로 나눠 순차 진행했습니다(차트 프리미티브는 데이터 레이어와 파일이 안 겹쳐 병렬로 같이 진행).

- **이벤트 트래킹**: `events/{eventId}` 컬렉션(append-only — 생성만 허용, 수정·삭제는 소유자에게도 금지). 스펙 생성/발행 토글/템플릿 가져오기 등 기존 동작 지점에 `trackEvent()` 호출만 추가.
- **집계는 클라이언트에서**: Cloud Functions 트리거나 별도 파이프라인 없이, 브라우저가 본인 이벤트를 읽어 직접 집계합니다 — 개인 데이터 규모에는 충분하고 "별도 백엔드 서버 없음" 원칙과 맞습니다.
- **퍼널의 한계를 숨기지 않음**: 이벤트에 `specId`가 없어서 "이 문서 하나의 정확한 경로"는 조인할 수 없습니다. 그래서 퍼널은 "같은 기간 단계별 이벤트 건수 비율"로 정직하게 좁혔고, 화면에도 그 한계를 캡션으로 명시했습니다 — 없는 정밀도를 있는 척하지 않는 쪽을 택했습니다.
- **리텐션은 이벤트가 아니라 스펙 자체를 씀**: `events` 대신 `specs`의 `createdAt`/`updatedAt`으로 "생성 주 코호트별로 N주 뒤에도 다시 손을 댔는지" 비율을 계산합니다 — 이벤트 로그의 조인 한계를 피해서 이미 있는 신뢰할 수 있는 데이터로 답을 냈습니다.
- **차트 라이브러리를 새로 안 넣음**: 4개 화면 전부 "크기 비교"가 목적이라(여러 카테고리를 구분하는 게 목적이 아님) `dataviz` 스킬의 색상 공식대로 기존 `primary` 파란 램프 하나만 쓰는 인라인 SVG로 직접 그렸습니다 — 바로 직전에 끝낸 번들 크기 최적화를 무의미하게 만들지 않기 위해서이기도 합니다.
